1. Introduction & Problem Statement The Core Problem

Introduction: When thousands of global users browse a mission-critical web server like the NASA Kennedy Space Center, the web server writes an entry for every single resource requested into an access log file.

The Big Data Problem: Over an extended period, this log grows into massive volumes (over 205 Megabytes containing 1.89 million records in our July 1995 dataset). Traditional data processing methods face severe limitations:

  • Memory Overflow: Loading millions of unstructured lines into memory in standard Python or Excel causes system crashes and out-of-memory errors.
  • Lack of Scalability: Single-threaded sequential processing cannot scale horizontally across cluster nodes as data volumes grow into gigabytes or terabytes.
  • Data Quality Issues: Real logs contain malformed requests, truncated end-of-file lines, internal quotations, and missing byte lengths (recorded as hyphens -) that break naive parsers.
The Illustrative Challenge: If 3 lines take a few seconds to calculate manually, analyzing 1,891,714 lines manually is completely impossible. We must automate extraction, aggregation, and visualization.
2. Project Goals & The 6 Research Questions Objectives

Primary Goal: Build a clean, distributed big data processing pipeline using Apache Hadoop MapReduce and Hadoop Streaming in Python to automatically extract operational intelligence from raw access logs.

Our Project Answers Six Specific Questions:

  1. When does the website receive the most requests? → Count request distribution by hour of the day (00 through 23 EDT).
  2. Which pages or resources are requested most often? → Identify and rank the top 10 most requested URLs.
  3. Which HTTP status codes occur most frequently? → Measure server success, redirects, client errors, and server errors.
  4. Which client IP addresses generate the most requests? → Identify the top 10 most active client hosts and proxies.
  5. How many response bytes does the server send each day? → Calculate total network bandwidth volume transferred per calendar date.
  6. What percentage of requests fail each day? → Compute daily HTTP error rate percentage for status codes 400–599.
3. Dataset Source & Format Specification NASA July 1995 Trace

Dataset Source: Internet Traffic Archive (ITA), sponsored by Lawrence Berkeley National Laboratory.

Collection & Context: Collected by Jim Dumoulin on the NASA Kennedy Space Center WWW server in Florida. Contributed by Martin Arlitt and Carey Williamson for their landmark 1996 ACM SIGMETRICS study on web server workload characterization.

Dataset Specifications:

  • Trace Window: 00:00:01 EDT on July 1, 1995 to 23:59:59 EDT on July 28, 1995.
  • Raw Line Count: Exactly 1,891,715 lines (205.2 MB uncompressed).
  • Valid Parsed Records: 1,891,714 records (100% verified).
  • Corrupted Lines: Exactly 1 line at the very end of the file (alyssa.p), caused by host server disk space exhaustion on July 28, 1995.

Sample Record (Common Log Format):

199.72.81.55 - - [01/Jul/1995:00:00:01 -0400] "GET /history/apollo/ HTTP/1.0" 200 6245

Field Breakdown: Client IP (199.72.81.55) • Timestamp (01/Jul/1995:00:00:01 -0400) • HTTP Request (GET /history/apollo/ HTTP/1.0) • Status Code (200) • Response Size (6245 bytes, with - safely mapped to 0).

4. How We Solved It (Hadoop MapReduce Architecture) Map • Sort • Reduce

Instead of processing logs with a monolithic in-memory script, we implemented the MapReduce programming model using Hadoop Streaming:

  • 1. Mapper Step: Reads log lines from standard input (sys.stdin), extracts the target key, and emits intermediate key-value pairs (e.g. for status codes: 200 1, 404 1, 200 1).
  • 2. Shuffle & Sort Step: The Hadoop framework automatically groups all values sharing the same key together: 200 [1, 1, 1], 404 [1].
  • 3. Reducer Step: Reads grouped keys from sys.stdin and performs streaming aggregation in $O(1)$ memory: 200 3, 404 1. For Top-10 queries, it maintains a bounded min-heap of size 10 to prevent high memory usage.
Clean 3-File Architecture in src/:
• log_parser.py: Parses Common Log Format safely.
• mappers.py: Implements the Map step for all 6 analyses.
• reducers.py: Implements the Reduce step for all 6 analyses.
5. What We Got: Key Findings & Measured Invariants Real Computed Results

1. Hourly Diurnal Cycle:
Traffic follows a sharp business workday pattern: minimum at 05:00 EDT (31,919 requests) and peak at 14:00 EDT (122,479 requests).

2. File Type Invariant:
The top resource was /images/NASA-logosmall.gif (111,388 requests). 8 of the top 10 URLs are GIF images, proving multimedia graphics dominate server load.

3. High Server Reliability:
89.95% of responses were HTTP 200 (Success) and 7.01% were HTTP 304 (Cache Hits). Overall error rates (4xx + 5xx) represented only 0.58% of total volume.

4. Client Concentration:
Four of the top five client hosts were Prodigy Services dial-up ISP web proxies (e.g. piweba3y.prodigy.com with 17,572 requests).

5. Space Shuttle Discovery Peak:
Total network volume was 36.04 GB (38.70 GB). The absolute peak occurred on July 13, 1995 (2.63 GB, 134,203 requests) due to the launch of Space Shuttle Discovery on STS-70.

6. Stable Error Rate:
Daily error rates averaged 0.575%, remaining strictly below 1.0% throughout the entire month.
